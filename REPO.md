# Repository layout

Where things are, and why they are there rather than somewhere else.

```
wingtoolui/
├── dist/                  the built tool — one HTML file, committed on purpose
├── src/
│   ├── core/              38 modules, one per chapter or concern
│   └── ui/                index.html, style.css, app.js
├── tests/                 five programs: the unit suite, the Phase 1 audit,
│                          the full pipeline, the reference sweep, the benchmark
├── tools/                 the other check stages, the interface harness,
│                          importers, figures, and the search tool
├── data/reference/        137 tables of published and supplied data, and
│                          the Swoop2's own files
├── docs/                  40 notes on what was built, and what it cost
├── build.py               bundles src/ into dist/, with a collision guard
├── package.json           named scripts; no dependencies to install
├── MANIFEST.txt           every file, generated
└── ROADMAP.md             done and open, item by item
```

## Why `dist/` is committed

The tool is a single offline HTML file, and the point of that is that someone
can download it and use it without Node, Python, or a build step. Committing
the build makes the repository usable by the people it is for. `.gitignore`
carries the line to exclude it, commented out, if that ever changes.

## Why `src/core/` is flat inside itself

Thirty-eight modules with no sub-folders. Grouping them by phase was tried on
paper and abandoned: `loads.js` is Phase 2 for line tension, Phase 3 for
attachment tabs and Phase 5 for the collapse envelope. Any grouping would put
half of it in the wrong place. One module per concern, named for the concern,
is easier to search — and `tools/find.mjs` searches doc comments, so the
folder structure is not carrying the discovery burden.

## Why the reference data is in the repository

Every scaling law, line-length law and load model here is checked against
published manufacturer data, and several were **corrected** by it. Without
`data/reference/` the test suite cannot run and the claims cannot be verified.
It is about 680 KB.

`data/reference/CATALOGUE.md` is generated by `node tools/catalogue.mjs` — do
not edit it by hand.

## Files that are generated, not written

| file | generated by |
| --- | --- |
| `dist/paraglider-design-tool.html` | `build.py` |
| `MANIFEST.txt` | `tools/manifest.mjs` |
| `data/reference/CATALOGUE.md` | `tools/catalogue.mjs` |
| `docs/*.svg` | `tools/make-diagrams.mjs` |

The self-audit checks `MANIFEST.txt` against what is actually present, so a
file added without regenerating it fails the check.

## If a checkout will not build

Run `npm run doctor` first. It checks the whole tree — layout, every file the
manifest promises, every module the build needs, the reference data, and the
Node version — and says what to do about what it finds.

A first user hit `7 of 33 core modules are missing ... layout 'flat'`. Nothing
was wrong with their machine: they had cloned a repository still holding the
**old flat layout**, in which those seven files had never been committed. The
build could only report what it personally needed, which reads like a bug in
the tool rather than a stale tree.

**A flat checkout cannot be repaired by adding the missing files.** Replace
the whole tree with a current release. The build says so now, and `doctor`
says it before the build is even reached.

## A note on history

This file used to describe a **flat** repository — every source file at the
top level, thirteen of twenty-five core modules never committed, and no build
script. The built tool still worked, which is why it went unnoticed for so
long. That is fixed; the layout above is what the project actually is.
